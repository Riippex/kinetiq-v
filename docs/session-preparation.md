# Session Preparation and Dynamic Mode

## User Journey

The phone is the primary session controller because it coordinates capture and supports detailed input. Before activity begins, it presents a preparation sheet with the accepted routine summary, estimated duration, exercises, intensity, coaching tone, capture and display devices, optional post-session photo prompt, and the session mode.

The TV presents a reduced remote-friendly flow with mode, intensity, and start controls. It reflects phone changes in real time and may start a prepared session. Alexa can start, pause, resume, skip an eligible challenge, or disable Dynamic mode after the corresponding integration is validated. A remembered configuration may accelerate preparation, but starting a session always creates a new immutable snapshot of the accepted routine and selected configuration.

The capture preview must identify and confirm the session target before movement observations count. Target confirmation is session-scoped and does not create a persistent biometric identity. Device readiness and target confirmation are separate from accepting a routine.

## Session Modes

`NORMAL` follows the prescribed routine with guidance and supported movement tracking. `DYNAMIC` follows the same prescription and inserts bounded game challenges selected from an approved catalog. Dynamic mode changes presentation and pacing; it cannot silently change the accepted training prescription.

The initial challenge types are:

- `HOLD_POSE`: maintain a supported pose for a stated interval.
- `MIRROR_POSE`: match a supported reference pose.
- `QUICK_REPS`: complete a small, bounded number of repetitions from an exercise already accepted for the session.
- `RECOVERY`: follow a short recovery prompt.

Challenge eligibility is constrained by the accepted routine, user exclusions, available space and equipment, session intensity, remaining time, and current Vision capabilities. The product owns selection, scheduling, scoring, and narration. Vision reports observations and confidence; it does not choose challenges or alter the routine.

Random selection is reproducible from a server-generated seed and a versioned challenge policy. Language-model output cannot directly insert an exercise or decide completion. Every challenge is resolved against catalog rules first.

If visibility or target confidence is lost, challenge timing pauses and the interface explains why. Tracking failure does not count as user failure and does not remove confirmed activity. Users may skip a challenge without penalty. Dynamic mode may be disabled during an active or paused session and the routine continues in Normal mode. A session prepared as Normal cannot enable Dynamic mode after it starts; the user selects it during preparation so the eligible plan is known in advance.

Scores describe game completion or supported movement matching. They are not assessments of exercise technique, health, or medical safety.

## Configuration Snapshot

Preparing a session creates a `READY` workout session owned by the authenticated user. It references one accepted routine version and stores:

- requested and currently active mode;
- intensity and coaching tone for this session;
- capture and optional display device selections;
- whether to offer the separate post-session photo flow;
- Dynamic frequency, allowed challenge types, scoring, and narration when applicable;
- the challenge policy version and random seed generated by the backend.

The idempotency key prevents repeated phone or TV requests from creating duplicate sessions. Starting or changing a session uses its expected revision. Configuration can be edited while the session is `READY`; starting freezes it. Persistent coaching preferences remain separate from per-session overrides.

## First Slice Boundaries

The initial executable slice implements session configuration invariants, PostgreSQL persistence, exact accepted-routine version lookup, authenticated GraphQL preparation, and idempotent request handling. Web and phone expose the detailed configuration flow. Fire OS and Vega foundations expose the reduced TV flow and keep camera setup on the phone.

Routine discovery and acceptance, client authentication bootstrap, device discovery, camera readiness, live synchronization, challenge scheduling, and post-session photo capture remain subsequent increments until implemented and verified. The Vega source template is versioned here, while its generated SDK project and device build must be created and validated on the Ubuntu Vega host.
